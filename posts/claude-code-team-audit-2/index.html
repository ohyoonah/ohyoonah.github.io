4편개인 업무에 붙이는 자동화

1편에서 확인한 건, 문서는 있는데 PR 시점에 그걸 검사하는 장치가 없다는 것이었다. 이번 편은 그 공백을 어떤 순서로 채울지다.

관찰 → 차단 → 생성

자동화에는 위험도가 다른 세 단계가 있다.

단계하는 일틀렸을 때 비용전제
관찰리포트만 남김무시하면 그만없음
차단조건 미충족 시 머지 불가잘못 막으면 개발 정지규칙이 정확해야 함
생성코드·PR·티켓을 만듦잘못된 산출물이 사람 시간을 먹음차단하는 검사가 먼저

우리는 PR 시점에 관찰조차 없었다. 빌드는 머지된 다음에야 돌아서 알려주기만 한다. 이 상태에서 생성 자동화(에이전트가 코드를 짜서 PR을 올리는 것)부터 붙이면 검증되지 않은 산출물이 검증되지 않은 채로 쌓인다. AI는 그럴듯하게 틀리기 때문에, 검사 없이 생성부터 자동화하면 실패가 증폭된다.

대화로 시킬 일과 코드로 남길 일

Claude에게 시킬 수 있는 일은 두 종류다. 구분을 안 하면 매번 돌아야 하는 검사를 매번 대화로 시키게 된다.

 대화로 시킨다코드로 남긴다
언제한 번 알아보면 되는 것매 PR마다 돌아야 하는 것
결과세션마다 조금씩 다르다항상 같다
비용호출할 때마다 토큰CI 실행 시간뿐
예이 규칙이 지켜지고 있나, 이 변경이 의도대로인가키 짝 검사, 하드코딩 색 검출

핵심은 둘을 잇는 것이다. 조사는 Claude에게 시키고, 그 결과를 스크립트로 받아서 CI에 건다.

예: i18n 키 짝 검사

CLAUDE.md는 노출 텍스트를 ko.json과 en.json 양쪽에 넣으라고 요구한다. 지켜지는지 Claude에게 대조를 시켰다.

1
2

ko 키: 2381 · en 키: 2392
en에 없는 키: 7 · ko에 없는 키: 18

여기까지는 파일 비교라 금방 나온다. 실제로 손이 가는 건 다음 단계였다. 어긋난 25건 중 11건은 아무도 안 쓰는 죽은 키라 지우면 끝이고, 문제는 코드가 실제로 호출하는 나머지 14건이다. 키마다 코드베이스를 뒤져야 알 수 있어서 사람이 하기엔 지루하고, Claude에게는 맞는 일이다.

방향에 따라 증상이 갈린다. 한국어에만 있는 3건은 fallbackLng: 'ko' 설정 때문에 영어 화면에 한국어가 그대로 나간다. 그중 둘은 단어 구분자가 갈라진 쌍이었다. 한쪽 파일에는 some_key로, 다른 쪽에는 some-key로 들어가 있어서 키가 두 개가 된 것이다. 사람 눈에는 같은 키로 보이고, 파일을 나란히 놓고 봐도 잘 안 걸린다.

영어에만 있는 11건은 폴백 대상인 한국어가 비어 있어서 증상이 다르다. 호출 방식에 따라 결과가 갈려서 화면을 봐야 정확히 알 수 있다. 어느 쪽이든 에러도 경고도 없다.

그런데 이 대조를 매 PR마다 Claude에게 시킬 수는 없다. 양쪽 합쳐 4700개 키를 매번 읽어야 해서 토큰이 들고, 더 나쁜 건 하나를 빠뜨려도 알 수 없다는 점이다. 그래서 같은 검사를 스크립트로 받아둔다.

// scripts/check-i18n.js (신규)
const flat = (o, p = '') =>
  Object.entries(o).flatMap(([k, v]) =>
    v && typeof v === 'object' ? flat(v, p + k + '.') : [p + k],
  );

const ko = flat(require('../src/translate/ko.json'));
const en = flat(require('../src/translate/en.json'));
const diff = (a, b) => a.filter((x) => !new Set(b).has(x));

const missing = [...diff(ko, en), ...diff(en, ko)];
if (missing.length) {
  console.error('i18n 키 불일치:\n' + missing.join('\n'));
  process.exit(1);
}

CI에 붙이려면 package.json에 "check:i18n": "node scripts/check-i18n.js"를 등록하고, 1편의 pr-check.yml에 실행을 추가한다.

1
2

      - run: yarn check:i18n
        continue-on-error: true   # 관찰 단계

continue-on-error가 관찰과 차단을 가르는 스위치다. 붙여두면 결과는 로그에 남지만 머지는 막지 않는다. 죽은 키를 지우고 쓰는 키를 정리한 뒤 이 줄을 빼면 차단으로 바뀐다. 다만 continue-on-error를 빼도 그것만으로는 머지가 막히지 않는다. 브랜치 보호에서 이 검사를 필수로 지정해야 한다. 확인해보니 main·staging·develop 세 브랜치 모두 보호 설정이 없어서, 지금은 검사가 빨간불이어도 머지된다. 로드맵 3번이 그 자리다. 처음부터 차단으로 걸면 기존 부채 때문에 모든 PR이 막힌다.

스킬로 만들면 안 되나

스킬은 사람이 부를 때만 돈다. PR 올리는 스킬에 검사를 끼워두면 빨리 알 수 있어서 좋지만, 스킬을 안 쓰고 손으로 PR을 올리면 그냥 지나간다. 지금 문제가 “사람이 lint:check를 기억해서 쳐야 한다”인데, 스킬로 옮기면 기억할 대상만 바뀐다.

그래서 둘을 같이 쓴다. 스킬은 PR 올리기 전 로컬에서 돌려 빨리 알려주는 쪽이고, CI는 그걸 안 썼을 때 막는 쪽이다.

도입 순서

앞의 것이 없으면 뒤의 것이 위험하거나 무의미해지는 순서로 놓았다.

순서항목근거
0AI 노출 정책 합의CLAUDE.md가 상수 파일에 민감 키가 있다고 적어뒀다. 그 파일은 git으로 추적되고 AI는 레포를 읽는다. 시크릿을 분리할지, 에러 수집에서 무엇을 걸러낼지 먼저 정한다
1정적 검사 도구 수리 → PR CI@typescript-eslint/parser가 없어서 babel 파서가 .tsx를 못 읽는다. 639건 중 552건이 파싱 실패. 고치기 전에 켜면 소음만 늘어난다

미룬 것

항목이유
서브에이전트 커스텀 정의컨텍스트 한계가 아니라 검사 부재가 병목
워크플로우 오케스트레이션1~4번이 없으면 실패를 증폭시킬 뿐
테스트 프레임워크 도입지금 없는 게 프레임워크가 아니라 검사를 돌릴 자리다

하지 않을 것

금지이유
에이전트에게 머지 권한검사가 없는 상태에서 최후 방어선까지 제거
파괴적 동작 자동 실행초기화·삭제는 사람 승인
배포 브랜치 간 자동 병합다른 티켓 커밋이 딸려감
핵심 의존성 자동 마이그레이션영향 범위를 AI가 판단할 수 없음
레거시 정리 자동 PR레거시 정리는 별도 티켓으로 하고 다른 변경에 묶지 말라는 팀 규칙이 있다

정리

  1. 자동화는 관찰 → 차단 → 생성 순서로. 검사 없이 생성부터 붙이면 실패가 증폭된다.
  2. 매 PR 돌아야 하는 검사는 Claude에게 스크립트를 짜게 해서 CI에 건다. 매번 대화로 시키지 않는다.

다음 편은 코드 바깥이다. 사람이 매번 같은 판단을 반복하는 절차를 다룬다.
