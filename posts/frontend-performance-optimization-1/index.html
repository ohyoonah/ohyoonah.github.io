프론트엔드 성능 최적화, 어디서부터 시작할까 (1) — 측정과 진단

성능 문제는 나중에 고치면 된다는 생각으로 미뤄두기 쉽다. 그러다 실제로 느리다는 피드백이 들어오면 뭐부터 봐야 할지 막막해진다. 그 전에 어디서부터 어떻게 접근할지 정리해두려 한다.

성능이 왜 중요한가

사용자 경험 차원의 이야기만이 아니다. 성능은 비즈니스 지표와 직결된다.

Google 연구에 따르면 페이지 로딩이 1초 지연될 때마다 전환율이 약 7% 감소한다. 모바일에서는 3초 안에 로딩되지 않으면 절반 이상의 사용자가 이탈한다. SEO에도 영향을 준다. Google은 Core Web Vitals를 검색 순위 요소 중 하나로 쓰고 있다.

성능 문제는 코드가 쌓이면서 서서히 생긴다. 처음엔 괜찮다가 어느 순간 체감할 만큼 느려지는데, 그 시점에 원인을 찾으려면 많은 시간이 든다.

성능 최적화는 문제가 생긴 뒤에 하는 것이 아니라, 기준을 잡고 주기적으로 확인하는 것이다.

측정이 먼저다

최적화를 시작할 때 흔히 하는 실수가 있다. 측정 없이 “이게 느릴 것 같다”는 직감으로 수정하는 것이다.

직감이 맞을 때도 있지만, 틀릴 때 더 많다. 실제로 느린 부분이 아닌 곳에 시간을 쏟게 된다. 측정 없이 최적화하면 개선됐는지 판단할 기준도 없다.

어디가 얼마나 느린지 수치로 확인한 뒤, 그 부분부터 건드리는 게 맞다.

그렇다면 무엇을 측정해야 할까. Google은 사용자 경험을 수치화하는 표준 지표로 Core Web Vitals를 정의하고 있다.

Core Web Vitals

세 가지 지표로 구성된다.

LCP (Largest Contentful Paint) 페이지에서 가장 큰 콘텐츠가 화면에 그려지는 시간. 로딩 체감 속도를 나타낸다.

  • 좋음: 2.5초 이하
  • 개선 필요: 2.5초 ~ 4초
  • 나쁨: 4초 초과

INP (Interaction to Next Paint) 사용자 인터랙션(클릭, 탭, 키 입력)에 반응해 화면이 업데이트되기까지의 시간. 2024년 FID를 대체했다.

  • 좋음: 200ms 이하
  • 개선 필요: 200ms ~ 500ms
  • 나쁨: 500ms 초과

CLS (Cumulative Layout Shift) 페이지가 로딩되는 동안 레이아웃이 얼마나 이동하는지 측정. 이미지, 광고, 동적 콘텐츠가 늦게 로딩되면서 기존 요소가 밀려나는 현상이다.

  • 좋음: 0.1 이하
  • 개선 필요: 0.1 ~ 0.25
  • 나쁨: 0.25 초과

Core Web Vitals는 이론적인 지표가 아니라 실제 사용자 경험과 SEO에 직접 영향을 주는 수치다.

Lighthouse를 실행하면 이 세 가지 외에도 FCP, TBT, Speed Index, TTI 같은 추가 지표들도 함께 표시된다.

Lighthouse로 현황 파악하기

Lighthouse는 Chrome 내장 도구로, 성능 점수와 개선 제안을 함께 제공한다.

Chrome DevTools → Lighthouse 탭 → Analyze page load를 실행하면 된다.

또는 CLI로 쓸 수도 있다.

1

npx lighthouse https://example.com --output html --view

결과에는 Performance, Accessibility, Best Practices, SEO 점수가 나오고, 각 항목별로 문제와 해결 방법이 함께 표시된다.

몇 가지 주의할 점이 있다.

  • 시크릿 창에서 실행한다. 확장 프로그램이 결과에 영향을 줄 수 있다.
  • 여러 번 실행해서 평균을 낸다. 네트워크 상태나 다른 탭의 영향으로 결과가 달라질 수 있다.
  • 개발 환경과 프로덕션 환경의 결과는 다르다. 소스맵, 디버그 코드, HMR 등이 빠지는 프로덕션 빌드에서 측정하는 것이 실제와 가깝다.
  • CPU Throttling을 설정하면 저사양 환경을 시뮬레이션할 수 있다. 기본값은 4x 감속이고, 6x로 높이면 더 엄격한 기준으로 측정된다. 내 개발 환경에서만 점수가 잘 나오는 상황을 막을 수 있다.

랩 데이터와 필드 데이터

Lighthouse는 내 환경에서 시뮬레이션해서 얻은 랩 데이터(lab data)다. 네트워크 속도, 디바이스 성능, 캐시 상태를 일정하게 고정하고 측정하기 때문에 재현 가능하고 비교하기 쉽다.

하지만 실제 사용자가 경험하는 수치와 다를 수 있다. 사용자마다 디바이스 성능이 다르고, 네트워크 환경도 다르다. Lighthouse 점수가 높아도 실제 사용자에게는 여전히 느리게 느껴질 수 있다.

실제 사용자 데이터(필드 데이터, field data)를 확인하는 방법이 따로 있다.

Google Search Console Search Console의 Core Web Vitals 리포트에서 실제 사용자가 경험한 LCP, INP, CLS 수치를 확인할 수 있다. 페이지별로 “좋음/개선 필요/나쁨” 분포도 볼 수 있다. 다만 데이터 반영까지 수일이 걸리기 때문에, GSC에서 문제를 발견했다면 Lighthouse로 로컬에서 재현하고 수정하는 흐름으로 접근하는 게 효율적이다.

web-vitals 라이브러리 프로덕션 코드에 직접 심어서 측정하는 방법도 있다.

1

npm install web-vitals

1

4
5

수집한 데이터를 분석 도구로 보내면, 실제 사용자 기준으로 어떤 페이지가 문제인지 파악할 수 있다.

Lighthouse 점수는 출발점이고, 실제 사용자 데이터가 목표 기준이다.

Chrome DevTools Performance 탭

Lighthouse가 “무엇이 문제인지” 알려준다면, Performance 탭은 “왜 느린지”를 파고드는 도구다.

페이지 로딩이나 인터랙션을 녹화하면 타임라인이 나온다. CPU 사용량, 스크립트 실행, 레이아웃, 페인트가 어느 시점에 얼마나 걸렸는지 ms 단위로 확인할 수 있다.

주로 확인하는 것들:

  • 롱 태스크(Long Task): 메인 스레드를 50ms 이상 점유하는 작업. 이 구간에서 사용자 인터랙션이 블로킹된다. 빨간 삼각형으로 표시된다.
  • 레이아웃 스래싱(Layout Thrashing): JS로 스타일을 읽고 쓰는 작업이 반복되면 레이아웃 계산이 연속으로 발생한다. 보라색 영역이 과하게 나타난다.
  • 불필요한 리페인트: 변경이 없는데 화면이 다시 그려지는 구간.

Lighthouse에서 “스크립트 실행 시간을 줄이세요” 같은 제안이 나왔을 때, Performance 탭으로 어떤 함수가 시간을 잡아먹는지 구체적으로 찾을 수 있다.

번들 크기 분석

초기 로딩이 느린 원인 중 상당수는 번들 크기에 있다. 필요하지 않은 코드까지 한꺼번에 내려받고 있거나, 같은 라이브러리가 중복으로 포함돼 있거나, 큰 라이브러리를 통째로 불러오는 경우가 많다.

webpack-bundle-analyzer

Webpack을 쓴다면 가장 많이 쓰는 도구다. 번들을 구성하는 각 모듈의 크기를 트리맵으로 시각화해준다.

1

npm install --save-dev webpack-bundle-analyzer

빌드를 실행하면 브라우저에 트리맵이 열린다. 어떤 라이브러리가 얼마나 차지하는지 한눈에 볼 수 있다. Vite를 쓴다면 rollup-plugin-visualizer로 동일하게 분석할 수 있다.

확인할 것들

  • 예상보다 훨씬 큰 라이브러리가 있는가
  • node_modules 안에 중복된 패키지가 있는가
  • 현재 페이지에 필요하지 않은 코드가 포함되어 있는가
  • moment.js, lodash처럼 부분만 써도 되는 라이브러리를 통째로 불러오고 있는가

번들 분석을 처음 해보면 예상보다 큰 덩어리를 발견하는 경우가 많다. 문제를 발견하는 것 자체가 최적화의 시작이다.

우선순위 잡기

측정 결과를 보면 손대고 싶은 곳이 여러 군데 보인다. 한꺼번에 다 고치려 하면 효과를 파악하기도 어렵고, 시간도 많이 든다.

우선순위를 잡는 기준을 정해두는 게 낫다.

1. 가장 많이 쓰는 페이지부터 모든 페이지를 최적화할 수는 없다. 사용자가 가장 많이 방문하는 페이지, 전환이 일어나는 핵심 페이지부터 시작한다.

2. 비용 대비 효과가 큰 것부터 번들에서 큰 비중을 차지하는 라이브러리 하나를 제거하거나, 코드 스플리팅으로 초기 로딩 크기를 줄이는 것처럼 적은 노력으로 큰 개선이 가능한 부분을 먼저 찾는다.

3. 수치로 비교할 수 있게 기록한다 최적화 전후 Lighthouse 점수와 번들 크기를 기록해둔다. 개선이 됐는지 확인하고, 팀 내에서 공유하기 위해서다.

측정과 진단만 제대로 해도 어디에 문제가 있는지 윤곽이 잡힌다. 2편에서는 실제로 번들 크기를 줄이는 방법, 코드 스플리팅과 lazy loading을 다룰 예정이다.
