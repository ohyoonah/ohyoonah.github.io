라이브코딩 테스트 vs 일반 코딩테스트 — 차이점과 준비 방법

개발자 채용 과정에서 코딩 테스트는 한때 거의 표준이었다. 최근엔 과제 전형이나 포트폴리오로 대체하는 회사가 늘었지만, 대기업·공기업 계열과 일부 테크 기업에서는 여전히 코테가 주요 관문으로 남아있다. 그런데 막상 준비하려고 보면 “라이브코딩”이라는 말이 따로 붙어있는 경우가 있다. 둘 다 코드를 짜는 거 아닌가 싶지만, 실제로는 평가 방식과 요구하는 역량이 꽤 다르다.

일반 코딩테스트

흔히 “코테”라고 부르는 것. 프로그래머스, LeetCode 같은 플랫폼에서 문제를 풀듯이, 정해진 시간 안에 알고리즘 문제를 풀어 제출하는 방식이다.

국내 알고리즘 플랫폼 백준은 2026년 4월 28일 서비스를 종료했다.

특징

  • 혼자서 푼다. 면접관이 없다.
  • 결과물(코드)로만 평가된다. 과정은 보이지 않는다.
  • 자동 채점. 통과/실패가 명확하다.
  • 시간은 보통 1~3시간.

주로 나오는 유형

유형예시
그래프/BFS/DFS최단 경로, 연결 요소
DP배낭 문제, 최장 부분 수열
구현/시뮬레이션게임 규칙 구현, 격자 이동
정렬/이분탐색커스텀 정렬, 범위 탐색
그리디최소 비용 선택, 구간 스케줄링
스택/큐/힙괄호 검사, 우선순위 처리

준비 방법

  1. 유형별 풀이 패턴을 외운다. BFS는 어떻게 짜는지, DP 점화식은 어떻게 잡는지 반복 훈련.
  2. 시간 복잡도를 항상 따진다. O(N²)이 통과될 N인지 먼저 확인하는 습관.
  3. 엣지 케이스를 먼저 생각한다. 빈 입력, 최솟값/최댓값, 순환 등.
  4. 꾸준한 반복. 하루 1~2문제씩 꾸준히 푸는 게 벼락치기보다 낫다.

라이브코딩 테스트

면접관이 지켜보는 상태에서 실시간으로 코드를 짜는 방식. Zoom, Google Meet 등 화상통화를 켜놓고, 코딩 플랫폼이나 공유 에디터(CoderPad, CodePair 등)에서 진행한다.

특징

  • 실시간으로 관찰된다. 생각하는 과정, 디버깅 방식, 소통 방식 모두 평가 대상.
  • 막히면 힌트를 주기도 한다. 완벽한 정답보다 문제 해결 접근법을 본다.
  • 시간은 보통 30분~1시간.
  • 문제 자체는 일반 코테보다 쉬운 경우가 많다.

실제로 평가하는 것

  • 커뮤니케이션: 풀이 아이디어를 말로 설명할 수 있는가?
  • 문제 분해 능력: 막막한 문제를 작은 단위로 쪼갤 수 있는가?
  • 디버깅 능력: 틀렸을 때 어떻게 원인을 찾는가?
  • 코드 품질: 변수명, 함수 분리 등 코드가 읽히는가?
  • 침착함: 긴장 상태에서도 논리적으로 생각하는가?

준비 방법

  1. 소리 내어 풀어라. 혼자 연습할 때도 “지금 이 배열을 순회하면서 조건에 맞는 것만 필터링하려고 합니다” 같은 식으로 말하면서 풀기.
  2. 문제를 받으면 바로 코드 짜지 말고 먼저 질문하라. 입력 범위, 엣지 케이스, 제약 조건을 확인하는 것만으로도 좋은 인상을 준다.
  3. 막히면 솔직하게 말해라. “지금 이 부분에서 막혔는데, 우선 브루트포스로 짜고 최적화하는 방향으로 가도 될까요?” 같은 식으로.
  4. 깔끔하게 짜는 연습을 한다. 일단 동작하게 짜되, 변수명과 함수 분리에도 신경 쓴다. 읽히는 코드가 같은 정답이라도 더 좋은 인상을 준다.
  5. CoderPad나 CodePair 환경에 익숙해져라. 자동완성이 없는 환경에서도 빠르게 짤 수 있어야 한다.

비교

 일반 코딩테스트라이브코딩 테스트
환경혼자, 플랫폼 자동 채점면접관 동석, 실시간 관찰

마치며

일반 코테는 알고리즘 실력을 쌓는 것이 핵심이고, 라이브코딩은 그 실력을 남 앞에서 발휘하는 능력이 핵심이다. 둘 다 결국 코드를 잘 짜야 하지만, 라이브코딩은 추가로 “함께 일할 수 있는 사람인가”를 본다는 점에서 다르다.

라이브코딩이 더 무섭게 느껴질 수 있지만, 반대로 실력이 조금 부족해도 소통과 접근 방식이 좋으면 만회할 수 있다. 문제를 혼자 끙끙대지 말고 생각을 소리내어 공유하는 연습을 꾸준히 해두자.
