1·2편은 없는 걸 찾고 채울 순서를 정하는 얘기였는데, 이번 편은 이미 쓰고 있는 것들이다. 규칙과 절차를 각각 어디에 두고 어떻게 부르는지 정리했다.

개발팀 작업 절차

기존에는 작업 하나를 맡아서 머지까지 가는 데 일곱 단계를 거쳤고, 그중 규칙이 정해진 단계를 스킬로 묶어서 지금은 다섯 단계가 됐다.

티켓 확인과 브랜치 생성이 /jira-branch 하나로 합쳐지고, PR 생성과 티켓 상태 갱신이 /jira-pr 하나로 합쳐졌다. 작업과 머지는 그대로 남았다.

리뷰는 만들지 않았다. Claude Code에 /review가 이미 있어서, 만들 자격이 있는지 따지기 전에 이미 있는지부터 보는 게 순서였다.

스킬로 옮긴 것

기획을 읽고 작업 범위를 판단하는 건 어차피 개발자가 해야 하는 일이다. 문제는 그 앞뒤에 붙는 손작업이었다.

Jira를 열어 티켓을 찾고, 설명과 상태를 확인하고, 브랜치 이름을 규칙에 맞게 지어서 만드는 것까지가 매번 반복됐다. PR 쪽도 마찬가지로 작업한 내용을 되짚어 요약하고, 본문 형식을 맞춰 쓰고, 티켓에 공유할 내용을 또 정리했다.

/jira-branch가 앞쪽을 걷어낸다. 티켓을 MCP로 읽어 제목과 설명, 담당자와 상태를 한 번에 보여주니 Jira를 왕복하지 않아도 된다. 브랜치는 티켓 제목에서 키워드를 뽑아 규칙대로 만들고, 최신화한 main에서 딴다.

/jira-pr이 뒤쪽을 걷어낸다. origin/develop 기준으로 커밋과 diff를 읽어 PR 본문 초안을 만들고, 티켓에 남길 요약까지 같이 뽑아준다. 빈 화면에서 시작하지 않는다는 게 차이다.

읽고 판단하는 건 그대로 사람이 한다. 요약은 파악을 대신하는 게 아니라 어디서부터 볼지 잡아주는 정도고, 범위를 어디까지로 볼지도 결국 사람이 정한다. PR에서 무엇을 공유할지도 초안을 보고 고른다.

규칙은 문서에, 절차는 스킬에

무엇을 스킬로 만들지는 절차가 있느냐로 갈랐다.

CLAUDE.md는 매 세션 자동으로 로드되고 스킬은 불러야 돈다. 그래서 확인할 항목 하나로 끝나는 규칙은 CLAUDE.md에 두고, 여러 단계를 거치는 절차만 스킬로 만들었다. 리뷰에서 같은 지적이 반복될 때도 스킬을 만들지 않고 CLAUDE.md에 항목을 추가한다.

그 밖에 트래킹 속성 이름을 짓는 규칙과 UI 작업 규칙도 스킬로 만들어뒀다. 절차가 아니라 규칙을 담은 것들이라 여기서는 자세히 다루지 않는다.

외부와 연결하는 것

외부 시스템은 MCP로 붙였다. .mcp.json에 jira와 github, 그리고 라이브러리 문서를 찾아오는 context7이 등록돼 있다.

/jira-branch가 티켓을 읽어오고 /jira-pr이 댓글을 남기는 것도 jira MCP를 통해서다. 스킬이 절차를 적고 MCP가 연결을 담당하니, 둘이 붙어야 실제로 돈다.

동시에 돌리는 것

독립적인 작업을 나란히 굴릴 때는 worktree를 쓰고, .claude/worktrees/에 세 개가 살아 있다. 브랜치를 왕복하지 않으니 작업 중인 변경을 stash 할 필요도 없다. 컨텍스트를 아끼는 쪽으로도 쓸모가 있는데, 그건 4편에서 다룬다.

정리

  1. 절차 없이 규칙만 있는 건 CLAUDE.md에 넣는다. 매 세션 자동으로 읽히니 부를 필요가 없다.
  2. 여러 단계를 거치는 절차는 스킬로 만든다. 읽고 판단하는 건 그대로 두고, 그 앞뒤의 손작업만 넘긴다.
  3. 만들기 전에 이미 있는지 본다. 리뷰는 기본 제공 스킬로 해결됐다.
  4. 스킬이 절차를 적고 MCP가 연결을 담당하니, 둘이 붙어야 실제로 돈다.
  5. 팀에 남길 것은 git이 추적하는 경로에 둔다. 개인 경로에 있으면 나만 쓰는 것으로 끝난다.

다음 편은 개인 쪽이다. 아침마다 반복되는 확인을 어떻게 줄일지, 그중 무엇은 계속 사람이 판단할지를 다룬다.
