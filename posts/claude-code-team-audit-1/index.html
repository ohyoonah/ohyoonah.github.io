팀에서 Claude Code를 몇 달 쓰다 보니 걸리는 지점이 생겼다. 코드는 잘 나온다. 그런데 그게 팀 규칙을 지켰는지, 실제로 도는지 검증되지 않은 채로 머지된다. 번역 파일을 한쪽만 채워도 빌드는 통과한다.

무엇이 빠져 있는지 확인해봤다.

CI/CD 워크플로우와 트리거 (push인가 pull_request인가).github/workflows/

필요한 건 CLAUDE.md를 더 두껍게 쓰는 게 아니었다. 문서는 이미 정확한데, 그게 지켜졌는지 확인하는 장치가 없었다.

급한 건 세 가지였다.

  1. PR 시점에 도는 검사가 0개 (빌드는 머지된 뒤에 돈다)
  2. 프로덕션 JS 에러 수집기 미설치
  3. i18n 키 불일치

세 개 다 AI 설정과 무관하다.

규칙을 지키게 하는 네 가지 방법

점검하면서 알게 된 게 있다. 우리 팀 규칙은 여러 곳에 흩어져 있는데, 어디에 적혀 있느냐에 따라 힘이 다르다.

규칙이 있는 곳사람이 바뀌면안 지켰을 때
내 컴퓨터 설정, 내가 쓰는 프롬프트사라진다아무 일도 없다
레포의 CLAUDE.md, 공유 스킬남는다아무 일도 없다
사람 리뷰남지만 사람에 달린다그냥 넘어간다
CI, 훅, 테스트남는다머지가 막힌다

아래로 갈수록 힘이 세진다. 맨 아래만 안 지키면 못 넘어가게 만든다.

우리는 문서와 사람 리뷰까지는 갖췄고, 맨 아래가 없었다.

구체적으로 무엇이 있고 없었나

있는 것.

빌드가 아예 안 도는 건 아니다. push 트리거라서 develop에 머지되면 그때 돈다. 문제는 두 가지다. 머지된 다음에 돌기 때문에 알려주기만 하고 막지는 못하고, 배포용 빌드라서 lint와 포맷 검사는 그 안에 들어 있지 않다.

그래서 이건 새로 만드는 문제가 아니라, 이미 있는 파이프라인을 PR 시점으로 한 번 더 당겨 붙이는 문제다.

도입 전후 비교

CLAUDE.md 최초 커밋 시점(2026.02)을 기준으로 앞뒤 5개월을 비교했다.

지표이전이후변화
커밋330486+47%
PR46150+226%
리뷰가 달린 PR34103+203%

커밋보다 PR이 훨씬 빠르게 늘었다. PR이 그만큼 잘게 쪼개졌다는 뜻이다. 작은 PR은 리뷰하기 쉽고 되돌리기도 쉽다.

리뷰가 잘 따라왔다. PR이 3배 넘게 늘면 보통 리뷰가 밀리는데, 리뷰가 달린 PR도 거의 같은 비율로 늘었다.

하지만 정작 알고 싶은 품질 변화는 측정할 수 없었다. 에러 수집기가 없어서 비교할 기준선이 아예 없다.

그래서 이 표는 효과를 증명하는 자료가 아니다. 앞으로의 변화를 재기 위한 출발점으로만 남겨뒀다.

어긋나도 티가 안 난다

CLAUDE.md가 참조하는 유틸 함수, 스킬, 라우트 경로를 하나씩 대조해봤는데 실재하지 않는 참조는 없었다. 낡은 경로 하나가 나온 게 전부다.

그래도 짚어둘 만하다고 본 건, 이런 어긋남이 생겨도 아무 신호가 없기 때문이다. 사람은 없는 명령을 치면 에러를 보고 알아차리지만, AI는 문서가 가리키는 스킬이나 경로가 사라져도 에러를 내는 대신 조용히 우회한다. 그러면 검증이 빠진 PR이 아무도 모르는 사이에 올라온다.

그래서 CLAUDE.md도 코드처럼 다루기로 했다. 참조하는 스킬·경로·도구가 실재하는지 분기마다 한 번씩 대조한다.

시키는 것과 막는 것은 다르다

우리 CLAUDE.md는 정적 검사를 맹신하지 말라고 한다. 이 스택에서는 tsc와 eslint가 제대로 돌지 않으니 런타임까지 확인하라고 적혀 있다. 그런데 바로 다음 줄에는 lint:check와 prettier:check를 돌리라고 명령까지 지정해뒀다.

문서는 돌리지 말라고 한 적이 없다. 빠진 건 그게 자동으로 돌지 않는다는 것이다. 사람이 기억해서 쳐야 하고, 안 쳤을 때 막아주는 것도 없다.

커밋 히스토리에 develop 빌드 실패 수정 — 중복 선언 제거가 있다. CD 빌드가 잡아주긴 했는데 머지된 다음이었고, 중복 선언은 lint가 먼저 잡는 종류다.

실행할 명령은 이미 package.json에 다 있다. lint:check, prettier:check, build:dev 셋 다 존재하고, 사람이 손으로 치면 지금도 돌아간다.

# .github/workflows/pr-check.yml (신규)
name: PR Check

on:
  pull_request:
    branches: [develop, staging, main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: yarn
      - run: yarn install --frozen-lockfile
      - run: yarn lint:check
      - run: yarn prettier:check
      - run: yarn build:dev

문서에 적는 것과, 통과해야 넘어가게 만드는 것은 다르다.

단, 처음부터 전체 검사로 차단하면 기존 부채 때문에 모든 PR이 막힌다. 걸기 전에 로컬에서 세 명령을 돌려보고, 걸리는 건수에 따라 변경 파일만 검사하거나 warning 허용으로 시작하는 게 안전하다.

리뷰에서 뭐가 걸렸나

티켓 하나에 딸린 PR 두 건을 리뷰했다. 표본이 작고 같은 기능 영역이라 일반화할 수는 없지만, 걸린 항목의 성격은 갈렸다.

코드 결함 — 예외 처리가 없어서 실패했을 때 다이얼로그에서 못 빠져나가는 것, 다이얼로그를 다시 열었을 때 이전 입력이 남아 재제출되는 것. 코드만 읽어도 잡히는 종류다.

경계 밖 문제 — 앱에서 넘어오는 상태 코드가 타입에 없는 값이었던 것, 확인 한 번에 비밀번호를 지우는 게 맞는지. 앞은 앱 코드를 봐야 알고 뒤는 사람이 정할 일이다. 둘 다 코드만 봐서는 판정이 안 된다.

후자가 있다는 게 이 리뷰의 수확이었다. 검사를 자동화할 때 코드 검사만 늘리면 이쪽은 계속 비어 있다.

걸린 자리도 겹쳤다. 둘 다 다이얼로그와 상태 전환 처리였다. 그래서 개별 버그로 닫지 않고 팀 체크리스트에 규칙으로 올렸다. 사람이 매번 기억하는 것보다 문서가 기억하는 게 싸다.

정리

  1. 문서는 충분했다. 없던 건 그 문서가 지켜졌는지 검사하는 장치다.
  2. 어긋나도 아무 신호가 없다. AI는 에러를 내는 대신 조용히 우회한다.
  3. 문서에 적는 것과 통과해야 넘어가게 만드는 것은 다르다.
  4. 커밋 수나 PR 수로는 AI 도입 효과를 말할 수 없다. 품질 지표가 먼저 있어야 한다.
  5. 코드만 봐서는 판정이 안 되는 지적이 있었다. 외부 계약과 제품 판단은 코드 검사로 커버되지 않는다.
  6. 지적이 겹치는 자리가 있으면 개별 버그로 넘기지 말고 규칙으로 옮긴다.

다음 편은 무엇을 어떤 순서로 자동화할지, 그중 무엇을 스크립트로 쓰고 무엇만 에이전트에게 맡길지다.
